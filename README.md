# 재고 차감 동시성 제어 프로젝트

## 프로젝트 목표

동시에 여러 사용자가 동일 상품을 주문할 때 발생할 수 있는 재고 정합성 문제를 재현하고, 여러 동시성 제어 방식의 장단점과 운영 적용 기준을 비교한다.

단순 구현이 아니라, Race Condition을 테스트로 증명하고 synchronized, Pessimistic Lock, Optimistic Lock을 단계적으로 적용하여 각 방식의 한계를 검증하는 것을 목표로 했다.

---

## 문제 상황

초기 구현은 상품을 조회한 뒤 재고를 차감하는 단순한 방식이었다.

```text
상품 조회 → 재고 확인 → 재고 차감 → 트랜잭션 커밋
```

단일 요청에서는 정상 동작하지만, 동시에 여러 요청이 들어오면 여러 트랜잭션이 동일한 상품 row를 동시에 조회하고 각각 차감한 뒤 커밋하면서 일부 변경 결과가 덮어써지는 Lost Update가 발생한다.

테스트 결과 초기 재고 100개에 대해 100개의 동시 차감 요청을 실행했을 때 기대 재고는 0이었지만, 실제 재고는 85로 남았다.

---

## 테스트 조건

* 초기 재고: 100
* 동시 요청 수: 100
* 요청당 차감 수량: 1
* 기대 결과: 최종 재고 0
* 실패 결과: 최종 재고 85

동시 요청은 `ExecutorService`와 `CountDownLatch`를 사용해 재현했다. `CountDownLatch`로 여러 스레드의 시작 시점을 맞춰 Race Condition 발생 가능성을 높였다.

---

## 테스트 실행 방법

전체 테스트 실행:

```bash
./gradlew test
```

Windows 환경:

```bash
gradlew.bat test
```

동시성 테스트는 초기 재고 100개를 생성한 뒤,
100개의 차감 요청을 동시에 실행합니다.

검증 기준:

* 락 없는 단순 차감: Lost Update 재현
* synchronized: 최종 재고 0
* Pessimistic Lock: 최종 재고 0
* Optimistic Lock: 재시도 후 최종 재고 0

테스트 내부에서는 `ExecutorService`와
`CountDownLatch`를 사용해 요청 시작 시점을 맞춥니다.

## 해결 방식 비교

### 1. 락 없는 단순 차감

상품을 조회한 뒤 재고를 차감하는 가장 단순한 방식이다. 단일 요청에서는 정상 동작하지만, 동시 요청에서는 여러 트랜잭션이 같은 재고 값을 읽고 수정하면서 Lost Update가 발생했다.

* 장점: 구현이 단순하다.
* 단점: 동시 요청에서 재고 정합성을 보장하지 못한다.
* 결과: 최종 재고 85로 실패

---

### 2. synchronized

Java의 `synchronized`를 사용해 단일 JVM 내부에서 한 번에 하나의 스레드만 재고 차감 로직에 진입하도록 제한했다.

* 장점: 구현이 단순하고 단일 서버에서는 정합성을 보장할 수 있다.
* 단점: 서버가 여러 대로 확장되면 각 서버의 lock 객체가 다르기 때문에 정합성을 보장할 수 없다.
* 결과: 최종 재고 0으로 성공

---

### 3. Pessimistic Lock

JPA의 `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 사용해 DB row 단위로 lock을 획득한 뒤 재고를 차감했다.

* 장점: DB row 기준으로 lock이 걸리기 때문에 서버가 여러 대여도 정합성을 보장할 수 있다.
* 단점: lock 대기, timeout, DB 부하가 발생할 수 있다.
* 적합한 상황: 재고, 쿠폰, 좌석 예약처럼 충돌 가능성이 높고 정합성이 중요한 도메인
* 결과: 최종 재고 0으로 성공

---

### 4. Optimistic Lock

JPA의 `@Version`을 사용해 version 값을 기준으로 충돌을 감지했다. 같은 version을 읽은 여러 트랜잭션 중 먼저 커밋한 트랜잭션만 성공하고, 나머지는 version 불일치로 실패한다. 실패한 요청은 재시도하여 최신 version 기준으로 다시 차감하도록 구현했다.

* 장점: DB row lock을 직접 잡지 않아 충돌이 적은 환경에서는 효율적이다.
* 단점: 충돌이 많으면 재시도가 증가해 성능이 떨어질 수 있다.
* 적합한 상황: 읽기가 많고 수정 충돌이 상대적으로 적은 도메인
* 결과: 최종 재고 0으로 성공

---

## 운영 적용 기준

재고 차감처럼 동시에 같은 row를 수정할 가능성이 높고 정합성이 중요한 기능은 Pessimistic Lock이 가장 단순하고 안정적이다.

Optimistic Lock은 충돌이 적은 환경에서는 효율적이지만, 선착순 주문이나 쿠폰 발급처럼 충돌이 집중되는 상황에서는 재시도 비용이 커질 수 있다.

synchronized는 단일 서버에서는 동작하지만 다중 서버 환경에서는 정합성을 보장하지 못하므로 운영 주문 시스템의 핵심 해결책으로는 적합하지 않다.

Redis Distributed Lock은 여러 서버에서 애플리케이션 레벨로 분산 락을 걸 수 있지만, TTL, lock 해제 실패, 장애 상황, 네트워크 지연 등을 함께 고려해야 하므로 별도 운영 설계가 필요하다.
