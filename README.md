# 재고 차감 동시성 제어 프로젝트

## 프로젝트 목표

동시에 여러 사용자가 동일 상품을 주문할 때 발생할 수 있는 재고 정합성 문제를 재현하고, 여러 동시성 제어 방식의 장단점과 운영 적용 기준을 비교한다.

단순 구현이 아니라, Race Condition을 테스트로 증명하고 synchronized, Pessimistic Lock, Optimistic Lock을 단계적으로 적용하여 각 방식의 한계를 검증하는 것을 목표로 했다. 모든 테스트는 최종 재고뿐 아니라 성공·실패 요청 수까지 함께 검증한다.

---

## 문제 상황

초기 구현은 상품을 조회한 뒤 재고를 차감하는 단순한 방식이었다.

```text
상품 조회 → 재고 확인 → 재고 차감 → 트랜잭션 커밋
```

단일 요청에서는 정상 동작하지만, 동시에 여러 요청이 들어오면 여러 트랜잭션이 동일한 상품 row를 동시에 조회하고 각각 차감한 뒤 커밋하면서 일부 변경 결과가 덮어써지는 Lost Update가 발생한다.

### 처음 실험에서 잘못 해석했던 부분

처음에는 JPA로 조회 후 차감하는 서비스로 "락 없는 상황"을 재현했고, 최종 재고가 0이 아니라 남는 결과를 Lost Update로 해석했다.

하지만 `Product` 엔티티에는 낙관적 락용 `@Version`이 선언되어 있다. 이 경우 JPA 변경 감지 UPDATE에 `WHERE version = ?` 조건이 붙기 때문에, 동시 요청은 서로를 덮어쓰지 않고 낙관적 락 예외로 실패한다. 테스트가 예외를 출력만 하고 넘어갔기 때문에, 실패한 요청을 덮어쓰기로 잘못 해석한 것이다.

그래서 두 경우를 분리했다.

* 진짜 무락: JDBC로 `SELECT stock` 후 `UPDATE ... SET stock = 읽은 값 - 1` (버전 조건 없음)
* JPA + `@Version` + 재시도 없음: 기존 단순 차감 서비스

그리고 모든 테스트에서 성공 요청 수와 예외 종류별 실패 수를 함께 집계하도록 바꿨다. Lost Update는 "모든 요청이 성공했는데 재고가 남는 것"으로, 낙관적 락 충돌은 "성공 수 + 남은 재고 = 초기 재고"로 구분된다.

---

## 테스트 조건

* 초기 재고: 100
* 동시 요청 수: 100
* 요청당 차감 수량: 1
* 기대 결과: 최종 재고 0, 성공 100건
* 측정 항목: 성공 수, 예외 종류별 실패 수, 최종 재고

동시 요청은 `ExecutorService`와 `CountDownLatch`를 사용해 재현했다. `CountDownLatch`로 여러 스레드의 시작 시점을 맞춰 Race Condition 발생 가능성을 높였다.

각 테스트는 `[방식] 성공=.., 실패=.. {예외 종류=건수}, 최종 재고=..` 형식으로 측정값을 출력한다.

Lost Update는 두 단계로 검증한다.

* 결정적 재현: 두 트랜잭션이 모두 재고를 읽을 때까지 `CyclicBarrier`로 기다린 뒤 각자 `읽은 값 - 1`로 덮어쓴다. 실행 환경과 관계없이 항상 재고 99가 남는다. 서비스 중간에 테스트용 훅을 넣지 않기 위해, 서비스와 같은 SQL 패턴을 테스트에서 직접 실행한다.
* 동시 100건 관찰: 실제 서비스에 동시 요청을 보낸다. 덮어쓰기 횟수는 스레드 스케줄링에 따라 달라지므로 재고 값은 단언하지 않고, 모든 요청이 성공했는지만 검증한 뒤 측정값을 출력한다.

## 해결 방식 비교

### 1. 락 없는 단순 차감

재고를 읽은 뒤, 읽은 값에서 수량을 뺀 결과로 덮어쓰는 가장 단순한 방식이다. 버전 검사가 개입하지 않도록 JDBC로 구현했다.

* 장점: 구현이 단순하다.
* 단점: 동시 요청에서 여러 트랜잭션이 같은 재고 값을 읽고 덮어쓰면서 Lost Update가 발생한다.
* 결과: 두 트랜잭션이 같은 값을 읽으면 둘 다 성공했는데도 차감 하나가 사라진다(재고 100 → 99). 동시 100건에서도 실패 요청 없이 재고가 남는다.

### 1-1. JPA 변경 감지 + `@Version` (재시도 없음)

처음에 "락 없음"이라고 생각했던 방식이다. 명시적 락은 없지만 `@Version` 때문에 실제로는 재시도 없는 낙관적 락으로 동작한다.

* 결과: 덮어쓰기는 없다. 성공한 요청 수만큼 정확히 차감되고, 나머지는 `ObjectOptimisticLockingFailureException`으로 실패한다.
* 의미: 정합성은 지켜지지만 사용자 요청이 실패한다. 4번에서 재시도를 붙인 이유다.

---

### 2. synchronized

Java의 `synchronized`를 사용해 단일 JVM 내부에서 한 번에 하나의 스레드만 재고 차감 로직에 진입하도록 제한했다.

* 장점: 구현이 단순하고 단일 서버에서는 정합성을 보장할 수 있다.
* 단점: 서버가 여러 대로 확장되면 각 서버의 lock 객체가 다르기 때문에 정합성을 보장할 수 없다.
* 결과: 최종 재고 0으로 성공

---

### 3. Pessimistic Lock

JPA의 `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 사용해 DB row 단위로 lock을 획득한 뒤 재고를 차감했다.

* 장점: DB row 기준으로 lock이 걸리기 때문에 서버가 여러 대여도 정합성을 보장할 수 있다.
* 단점: lock 대기, timeout, DB 부하가 발생할 수 있다.
* 적합한 상황: 재고, 쿠폰, 좌석 예약처럼 충돌 가능성이 높고 정합성이 중요한 도메인
* 결과: 최종 재고 0으로 성공

---

### 4. Optimistic Lock

JPA의 `@Version`을 사용해 version 값을 기준으로 충돌을 감지했다. 같은 version을 읽은 여러 트랜잭션 중 먼저 커밋한 트랜잭션만 성공하고, 나머지는 version 불일치로 실패한다. 실패한 요청은 재시도하여 최신 version 기준으로 다시 차감하도록 구현했다.

* 장점: DB row lock을 직접 잡지 않아 충돌이 적은 환경에서는 효율적이다.
* 단점: 충돌이 많으면 재시도가 증가해 성능이 떨어질 수 있다.
* 적합한 상황: 읽기가 많고 수정 충돌이 상대적으로 적은 도메인
* 결과: 최종 재고 0으로 성공

---

### 검토한 대안: 조건부 UPDATE

조회 후 차감하지 않고, 검사와 차감을 UPDATE 한 문장으로 처리하는 방식이다. 이 프로젝트에서는 구현하지 않고 비교 대상으로만 정리했다.

```sql
UPDATE product
   SET stock = stock - :quantity
 WHERE id = :id
   AND stock >= :quantity
```

* 같은 row의 UPDATE는 DB가 행 락으로 순서대로 처리하므로 Lost Update가 없고, 영향받은 행이 0이면 재고 부족이다.
* 조회와 수정 사이의 경합 구간이 없고 재시도도 필요 없어서, 단순 감소 연산에는 가장 짧은 락 구간으로 정합성을 보장한다.
* 대신 차감 로직이 SQL로 옮겨가 엔티티 검증을 거치지 않는다. JPQL 벌크 UPDATE로 구현하면 영속성 컨텍스트와 `@Version`을 우회하므로 version 증가를 직접 처리해야 한다.
* 실무에서 접수번호 중복 문제의 근본 해결안으로 정리한 "번호 행을 UPDATE로 먼저 증가시킨 뒤 읽는 방식"과 같은 원리다.

## 운영 적용 기준

재고 차감처럼 동시에 같은 row를 수정할 가능성이 높고 정합성이 중요한 기능은 Pessimistic Lock이 가장 단순하고 안정적이다.

Optimistic Lock은 충돌이 적은 환경에서는 효율적이지만, 선착순 주문이나 쿠폰 발급처럼 충돌이 집중되는 상황에서는 재시도 비용이 커질 수 있다.

synchronized는 단일 서버에서는 동작하지만 다중 서버 환경에서는 정합성을 보장하지 못하므로 운영 주문 시스템의 핵심 해결책으로는 적합하지 않다.

Redis Distributed Lock은 여러 서버에서 애플리케이션 레벨로 분산 락을 걸 수 있지만, TTL, lock 해제 실패, 장애 상황, 네트워크 지연 등을 함께 고려해야 하므로 별도 운영 설계가 필요하다.
